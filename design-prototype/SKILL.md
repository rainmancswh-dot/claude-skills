# Design Prototype Skill

从上游规格文档提取设计输入，生成标准化的 open-design 提示词，校验产物，归档。

## When to Apply

- 用户说"生成原型"、"做前端原型"、"open-design"
- api-design 和 flow-extract 都已完成之后

Do NOT apply when:
- 缺少 api-contract.yaml 或 flows.md
- 用户只想讨论设计，不生成原型

## Trigger

```
/design-prototype
```

---

## Phase 1: 读取上游文档

### 1.1 检测项目根目录

```bash
PROJECT_ROOT=$(git rev-parse --show-toplevel 2>/dev/null)
if [ -z "$PROJECT_ROOT" ]; then
  echo "ERROR: Not in a git repo"
  exit 1
fi
```

### 1.2 确认必要文档存在

```bash
[ -f "$PROJECT_ROOT/docs/api-contract.yaml" ] && echo "✅ docs/api-contract.yaml" || { echo "❌ docs/api-contract.yaml not found — 先跑 /api-design"; exit 1; }
[ -f "$PROJECT_ROOT/docs/flows.md" ] && echo "✅ docs/flows.md" || { echo "❌ docs/flows.md not found — 先跑 /flow-extract"; exit 1; }
[ -f "$PROJECT_ROOT/docs/DESIGN.md" ] && echo "✅ docs/DESIGN.md" || echo "⚠️ docs/DESIGN.md not found"
[ -f "$PROJECT_ROOT/CONTEXT.md" ] && echo "✅ CONTEXT.md" || echo "⚠️ CONTEXT.md not found"
```

### 1.3 读取并存储

完整读取所有存在的文档。

---

## Phase 2: 组装 open-design 提示词

### 2.1 提取页面清单

从 flows.md 提取所有路由和页面名称：

```bash
grep -E "^## Flow:|Route:" "$PROJECT_ROOT/docs/flows.md"
```

### 2.2 提取交互断言

从 flows.md 提取每个页面的 `[预期]` 断言，按页面分组。

### 2.3 提取 CSS Token

从 DESIGN.md 提取 CSS 变量定义：

```bash
grep -E "var\(--" "$PROJECT_ROOT/docs/DESIGN.md" | sort -u
```

### 2.4 提取领域术语

若 CONTEXT.md 存在，提取核心术语用于界面文案。

### 2.5 提取组件模式

从 DESIGN.md 提取已定义的组件模式（StatusPill、空状态、骨架屏等）。

### 2.6 生成提示词

将上述内容组装为以下结构的提示词，输出到终端供用户复制使用：

```
你是前端设计师。根据以下规格文档设计一个完整的 Web 原型。

## 项目信息
{从 DESIGN.md 提取的项目描述}

## 领域术语（必须使用）
{从 CONTEXT.md 提取的术语表}

## 页面清单
{从 flows.md 提取的所有页面路由和名称}

## 交互要求（MUST HAVE）
{从 flows.md 提取的所有 [预期] 断言，按页面分组编号}

## CSS Token（必须使用 var(--xxx) 引用）
{从 DESIGN.md 提取的 token 列表}

## 组件模式（必须复用）
{从 DESIGN.md 提取的已有组件模式}

## 输出要求
1. 每个页面对应一个独立的 HTML 文件
2. 所有颜色通过 CSS Token 引用：var(--xxx)，禁止硬编码色值
3. 实现所有 [预期] 断言中描述的交互行为
4. 使用领域术语表中的规范命名，禁止自创同义词
5. 包含所有页面状态的 UI：loading、empty、error、正常
6. 弹窗用 <dialog> 或 Modal 组件，禁止 prompt()/alert()
7. 页面之间可通过路由切换（SPA 单页应用方式或独立文件均可）
```

提示词输出后 STOP，等用户在 open-design 中运行。

---

## Phase 3: 校验产物

用户完成 open-design 后，将产物放到本机。手工指定产物路径，然后执行检查。

### 3.1 接收产物

请用户提供 open-design 产出的目录路径或文件列表：

> 请提供 open-design 产出的文件。可以是目录或单个 HTML 文件路径。

### 3.2 Check: 页面完整性

```bash
# 从 flows.md 提取预期页面数
EXPECTED_PAGES=$(grep -c "^## Flow:" "$PROJECT_ROOT/docs/flows.md")
# 统计产物中的页面文件数
ACTUAL_FILES=$(find "$DESIGN_OUTPUT_DIR" -name "*.html" | wc -l | tr -d ' ')
echo "预期页面: $EXPECTED_PAGES, 实际 HTML: $ACTUAL_FILES"
```

输出：
```
页面完整性:
预期 6 个页面 (flows.md)，实际 5 个 HTML 文件:
✅ /
✅ /templates
✅ /templates/:id
❌ /projects — 缺失
✅ /audit-log
✅ /errors
```

### 3.3 Check: CSS Token 合规

```bash
# 检查 HTML 中是否使用 var(--xxx) 而非硬编码颜色
grep -rnE "#[0-9a-fA-F]{3,6}|rgb\(|hsl\(|oklch\(" "$DESIGN_OUTPUT_DIR" --include="*.html" | grep -v "var(--" | grep -v "/\*"
```

输出：
```
CSS Token 合规:
✅ 无硬编码颜色，全部使用 var(--xxx)
```

### 3.4 Check: 术语合规

若 CONTEXT.md 存在，检查 HTML 中的文案是否使用了规范术语（而非 Avoid 列表中禁止的同义词）。

### 3.5 Check: 交互覆盖

逐条检查 flows.md 的 [预期] 断言是否在 HTML 中有对应实现。

输出：
```
交互覆盖:
✅ #1 骨架屏加载
✅ #2 空状态文案
❌ #3 弹窗确认 — 未找到 dialog/modal
...
总计: 17/18 通过, 1 未通过
```

---

## Phase 4: 归档

### 4.1 复制到项目目录

```bash
mkdir -p "$PROJECT_ROOT/docs/prototype"
cp -r "$DESIGN_OUTPUT_DIR"/* "$PROJECT_ROOT/docs/prototype/"
```

### 4.2 生成提示词归档

将 Phase 2 生成的 open-design 提示词保存：

```bash
echo "$OPEN_DESIGN_PROMPT" > "$PROJECT_ROOT/docs/open-design-prompt.md"
```

### 4.3 生成校验报告

```bash
cat > "$PROJECT_ROOT/docs/prototype/VERIFY_REPORT.md" << 'EOF'
# Prototype Verify Report

{Phase 3 的检查结果}

## 已知未覆盖项
{列出所有未通过的 [预期] 断言，供 downstream 开发时手动处理}
EOF
```

### 4.4 Commit

```bash
cd "$PROJECT_ROOT"
git add docs/prototype/ docs/open-design-prompt.md
git commit -m "feat: add design prototype generated by /design-prototype"
```

## 重要规则

1. **提示词必须包含所有 [预期] 断言。** 漏掉的交互动画在开发阶段难补。
2. **CSS Token 是硬约束。** 原型中的颜色都必须用 var(--xxx)，养成习惯。
3. **校验报告不隐瞒缺口。** 即使有未覆盖项，如实记录后仍可归档。
4. **原型不替代前端开发。** 原型是交互验收工具，开发时按 spec-dev 流程重新实现。
5. **产物目录固定。** 始终归档到 `docs/prototype/`，方便 downstream 查找。
